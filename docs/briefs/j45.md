# Brief — J45 (Effect rewrite of diet-f45)

## Intent

The project is renamed **J45** as part of this reset (formerly diet-f45).
diet-f45 started as a disposable travel utility: an F45-style synced workout timer
so two phones could run the same class without the gym. It worked well enough that
it's now a daily driver — the owner and his girlfriend are considering canceling
their F45 membership and using this full-time. That demands a different level of
craft than a toy.

This intake is a **full architectural reset**: rewrite the app in Effect-TS,
maximally — the rewrite itself is a primary goal (learning to work with Effect via
a coding agent), alongside turning the app into something substantial enough to
share with friends and family and grow new capabilities: per-user workout
libraries, structural control over workout flow, and quasi-infinite procedural
workout generation.

## Users

- **The owner and his girlfriend** — primary, multiple sessions per week, usually
  working out together off one synced timer, phones in hand, mid-workout (sweaty,
  low patience for friction).
- **Friends and family** — invited users with their own accounts, plans, and
  history; may join each other's live sessions.
- **"Maybe broader" someday** — explicitly not designed for now, but the design
  shouldn't paint itself into a corner that forbids it.

## Scope envelope

**Whole-project rewrite, full vision, dependency-ordered.** One project covering:

1. Effect-TS rewrite of the whole system at feature parity (typed domain model,
   synced sessions, plan editing, timers/beeps).
2. Accounts and per-user plan libraries.
3. Live session join that is *really easy* (one tap for a logged-in user).
4. Structural flow control (sets↔laps reflow, regrouping exercises into pods) at
   edit-time and launch-time.
5. Rule-based procedural workout generation from a tagged exercise library.
6. Per-user workout completion log.
7. Low-friction deployment to the owner's VPS.
8. Exercise animations shown during the workout, sourced from a pre-existing
   dataset — conditional on a source existing that isn't ugly (see Decided).

**Explicitly out of scope:**

- Public/broad multi-tenancy (open registration, strangers) — future intake.
- The standalone offline single-file player (`program/workout-plan.html`) — dropped;
  the app requires the server to be reachable.
- Per-exercise performance tracking (reps/weights logged) — future intake if ever.
- LLM-backed workout generation — future intake; rule-based first.
- Native mobile apps — the browser (phone-first) remains the client.

## Decided

- **Rewrite is a primary goal in itself.** Learning Effect-TS with a coding agent
  is part of the point; architectural concerns can be adjusted at will. Total reset.
- **Effect everywhere, maximally.** Push Effect into every corner deliberately:
  @effect/platform for HTTP, effect/rpc (or equivalent) between client and server,
  Stream-based sync, atom-based Effect state in the UI. Bleeding-edge pain is
  accepted as part of the experiment. Shared Schema domain model across client and
  server.
- **React** on top of the Effect client core (@effect-atom/atom-react is the
  maintained first-class binding).
- **Bun** as runtime and toolchain — on the VPS (@effect/platform-bun) and for
  dev tooling/package management.
- **shadcn/ui** as the UI component framework, initialized from the owner's
  preset: `bunx --bun shadcn@latest init --preset b7BYO1Ags --template vite`
  (Vite template).
- **Liquid glass aesthetic.** Mix in the liquid-glass effect the owner built in
  `~/Git/personal-site/` (`src/glass.ts` + `glass.frag.glsl` — a WebGL port of
  Aave's "Building Glass for the Web": real refraction, chromatic aberration at
  the rim, CSS frost fallback). Parts are coupled to that site's contour-field
  scene; how much ports versus adapts is Design's call. Effects must not
  compromise timer performance or battery on phones mid-workout, and the CSS
  fallback path matters.
- **Exercise animations, conditionally.** During a workout, show an animation
  of the current exercise when a decent one exists. Sourced from a pre-existing
  dataset — NOT hand-authored. Candidates found: free-exercise-db (public
  domain, ~800 exercises, static image pairs), ExerciseDB (1,300+ with GIFs),
  wger's open dataset. The bar: available from an existing source AND not super
  ugly; if no source clears the bar, the feature ships without animations.
  Source selection, licensing check, and how library exercises map to dataset
  entries are Design's.
- **SQLite via @effect/sql** for persistence — single-file DB on the VPS, real
  transactions, migrations in-repo.
- **Tenancy: per-user, solo-first, with ad hoc session joins.** Every user has
  their own plans, sessions, and history. A live synced session is something you
  invite others into. Joining must be REALLY easy — but **accounts are required
  for everything**: first-timers register (simple registration, friends/family
  scale); once logged in, joining a live session is one tap (e.g. code/QR/link —
  exact UX is Design's).
- **Flow control is first-class and structured.** A workout's flow (laps vs sets,
  pod groupings, work/rest ladders) is data you can transform: permanently
  restructure a saved plan, or apply a one-off reflow at session launch without
  touching the saved plan. Canonical example: 4 consecutive sets of push-ups →
  4 laps around a pod of push-up/sit-up/squat.
- **Procedural generation is rule-based.** A tagged exercise library (muscle
  group, equipment, cardio/strength, intensity) plus structural templates
  (pods, laps/sets, timing ladders); the generator composes them under
  constraints (focus, duration, available equipment, no-repeat-recently).
  Deterministic and testable. No LLM in the loop.
- **History: completion log.** Each session records, per participant, which
  workout, when, and how far they got. Powers no-repeat-recently generation
  constraints and a simple history view. No per-exercise data.
- **Parity edges:** the authored 3-week program content (base plan merged with
  the owner's overrides) migrates into the new DB as seed plans; the manual
  ad-hoc timer survives as a feature; the offline single-file player is dropped.
- **Quality bar:** domain logic (segment building, reflow transforms, generator,
  session state machine) fully unit-tested with @effect/vitest;
  schema-validated boundaries; code held to idiomatic Effect patterns (the
  vendored effect-deep-audit bar); typecheck + tests gate every merge; PLUS a
  comprehensive browser e2e suite (timer runs, session sync, editing flows).
- **Renamed to J45.** The rewrite ships under the name J45; "diet-f45" retires
  with the old app. Package name, UI branding, and repo naming follow (repo
  rename timing is the owner's call).
- **Build, don't buy.** Surveyed the market: synced gym-display timers
  (GymNext, CloudFit, StageTimer) and custom interval apps (Seconds, Interval
  Timer X, Gym Timer X's free F45 timer) exist, but nothing combines
  self-hosted + multi-phone server-authoritative sync + F45 pod/lap/set
  semantics + structural reflow + per-user libraries + generation — and buying
  wouldn't serve the learning goal.

## Deferred (deliberately left for Design)

- Exact Effect library choices at each layer (effect/rpc vs plain
  @effect/platform HTTP + SSE streams; atom library version; test runners).
- Exercise-animation source selection: quality/licensing vetting of
  free-exercise-db / ExerciseDB / wger (or others), and the mapping from the
  app's exercise library to dataset entries.
- How much of the personal-site liquid-glass implementation ports directly vs
  gets adapted (the refraction card technique is portable; the contour-field
  backdrop is site-specific).
- Auth mechanism details (password vs passkey; session management) — must fit
  "simple, friends/family scale, no email infrastructure required."
- Join UX (short code vs QR vs link — or several).
- The deployment mechanism satisfying the low-friction constraint (see
  Constraints), e.g. git-push deploy, single-artifact copy, or container.
- Domain model details: how flow/reflow transforms are represented so both
  edit-time and launch-time application fall out naturally.
- Generator constraint model specifics and the exercise-tagging taxonomy.
- Migration tooling for the existing workouts.json + overrides.json content.
- e2e tooling choice (Playwright presumed, Design decides).
- Whether the server remains the single clock of record and how client
  countdown smoothness is achieved in the new stack (current design: server
  timers + client rAF interpolation — a good baseline to keep or beat).

## Assumptions (unverified, proceeding on)

- Friends/family scale: tens of users at most, a handful of concurrent live
  sessions; a single VPS and SQLite comfortably cover it.
- Phone browsers are the only client that matters; PWA niceties (wake lock,
  audio beeps that actually sound) are parity requirements, not extras.
- The owner's VPS (with Caddy already in front) remains available and is the
  only deploy target.
- The current app can keep running during the rewrite; cutover happens when
  the new app reaches parity (side-by-side on the VPS until then).
- Effect's bleeding-edge corners (rpc, atom) are stable enough to build a
  daily-driver on; where they aren't, falling back one notch (e.g. plain
  platform HTTP) is acceptable without re-defining the project.

## Constraints

- **Self-hosted on the owner's VPS**, behind existing Caddy. No managed cloud
  services, no external SaaS dependencies for core function.
- **Deployment must be absolute lowest-friction** — current deploys are
  cumbersome and that pain is explicitly called out. Target: one command from
  laptop to live, seconds not minutes, safe to run many times a day.
- **Effect-TS maximally, React, SQLite, Bun, shadcn/ui (Vite)** as decided
  above.
- **No LLM/API-key dependencies** for core features.
- **No email infrastructure** (registration can't depend on sending mail).
- Bun runs on the VPS; the app must be cheap to run (it shares the box), and
  visual effects must stay cheap on phones mid-workout.

## Done looks like

- Two phones in a garage run the same workout in lockstep: one user starts a
  session, the other joins in one tap after logging in, both see the same
  countdown, beeps fire in sync, pause/skip/prev from either phone affects both.
- A new friend can be given the URL and be working out inside two minutes,
  including registration.
- Any workout from the old 3-week program is runnable in the new app,
  timing-identical to the old one.
- The owner can take "4 sets of push-ups" and run it as "4 laps of
  push-up/sit-up/squat" without editing the saved plan — and can also make that
  change permanent when wanted.
- "Generate me a 45-minute hybrid workout with dumbbells and a kettlebell"
  produces a runnable, sensible workout that avoids exercises done in recent
  sessions, and can do so effectively forever without repeating a workout.
- Each user can see what workouts they've completed and when.
- During a workout, the current exercise shows an animation when the chosen
  dataset has a decent one; its absence never blocks or clutters the timer.
- The UI is built from shadcn/ui components with the liquid-glass look mixed
  in, and stays smooth on phones.
- A code change reaches the live VPS with a single command in under a minute.
- The full test suite (unit + browser e2e) passes on every merge; the codebase
  reads as idiomatic Effect throughout.
- The old app is retired; the new one is the daily driver.
